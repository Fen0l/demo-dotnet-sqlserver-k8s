# SqlProbe — a .NET app on NKP logging in to SQL Server with an Active Directory account

PoC: an ASP.NET Core (.NET 10) service runs as a Linux pod on Nutanix Kubernetes
Platform (NKP) and logs in to an external, domain-joined Microsoft SQL Server as an
**Active Directory user**, with Kerberos. The account's username and password live in
CyberArk, reach the cluster through Vault and External Secrets, and are used only by the
container's entrypoint to obtain and renew the Kerberos ticket. The application process
itself never sees the password.

The app is deliberately small. Every endpoint exists to prove *that* the login works
and *how*: SQL Server reports the authentication scheme of the session
(`KERBEROS` or `SQL`), and the app shows it to you.

```
   NKP workload cluster (Linux pod)                     ITCS Active Directory            SQL Server (Windows,
 ┌────────────────────────────────────┐                 ┌──────────────────┐             domain-joined)
 │ container sqlprobe                 │   1. kinit      │ KDC              │            ┌──────────────────┐
 │  entrypoint.sh ── user+pw (Secret)─┼── 88/tcp ──────►│ fs2.itcs.local   │            │ SPN              │
 │      │  writes ticket cache        │ ◄── TGT ────────│ 10.12.54.14      │            │ MSSQLSvc/        │
 │      ▼  renews every 4 h           │   2. ticket for │                  │            │  sql01.itcs.local│
 │  app (.NET 10, SqlClient/GSSAPI) ──┼── MSSQLSvc/… ──►│                  │            │  :1433           │
 │                                    │ ◄── svc ticket ─│                  │            │                  │
 │                                    │   3. TDS login + ticket ── 1433/tcp ──────────►│ login ITCS\      │
 └────────────────────────────────────┘                                                 │  svc-sqlprobe    │
                                                                                        └──────────────────┘
```

## 1. How the Kerberos login works

Windows authentication *is* Kerberos. The client never sends a password to SQL
Server. It proves its identity to the domain controller once, receives tickets,
and hands SQL Server a ticket that only SQL Server's own account can decrypt.
SQL Server trusts the domain controller, so it trusts the name inside the ticket.

### The three exchanges

| # | Who talks to whom | What happens |
|---|---|---|
| 1 | pod → KDC (AD DC, port 88) | `kinit` proves "I am `svc-sqlprobe@ITCS.LOCAL`" with the account's **password** (from the mounted Secret). The KDC returns a **TGT** (ticket-granting ticket), valid 10 h. It is stored in a file, the *credential cache*. |
| 2 | app → KDC | When the app opens the connection, Microsoft.Data.SqlClient (via GSSAPI / MIT Kerberos) asks the KDC for a *service ticket* for the name `MSSQLSvc/<sql-fqdn>:<port>`. The KDC finds which AD account owns that **SPN** and encrypts the ticket with that account's key. |
| 3 | app → SQL Server (port 1433) | The ticket goes inside the TDS login packet. SQL Server, running as the account that owns the SPN, decrypts it, reads `ITCS\svc-sqlprobe`, and matches it to a login created with `CREATE LOGIN [ITCS\svc-sqlprobe] FROM WINDOWS`. The session's `auth_scheme` is `KERBEROS`. |

### The pieces and why each exists

| Piece | Role | Where it lives here |
|---|---|---|
| **AD service account** `svc-sqlprobe` | the identity the pod logs in as; password owned and rotated by **CyberArk** | `ad/01-prepare-ad.ps1` or `scripts/create-ad-account-ldap.sh` |
| **credentials Secret** `sqlprobe-ad-credentials` | username + password, mounted as files at `/krb5/creds` | written by External Secrets from Vault (`k8s/25-externalsecret.yaml`), or by `scripts/make-ad-secret.sh` for a test |
| **SPN** `MSSQLSvc/sql01.itcs.local:1433` | tells the KDC whose key encrypts the service ticket. It belongs to the account **SQL Server runs as** (its own service account), not to the app account, and is normally already registered by the SQL Server setup. Nothing to register for `svc-sqlprobe`. Only if it is missing does Kerberos fail | verify with `setspn -Q` (`ad/01-prepare-ad.ps1` checks it) |
| **krb5.conf** | realm name, KDC address, and options that stop Linux from rewriting the host name before building the SPN | generated by `entrypoint.sh` from `KRB5_USER` + `KRB5_KDC` |
| **FQDN in the server name** | it *becomes* the SPN. An IP or short name asks for `MSSQLSvc/10.x.x.x:1433`, which nobody registered | `SQLPROBE_SERVER` in `k8s/10-config.yaml` |
| **Windows login on SQL Server** | maps the Kerberos name to a SQL principal | `ad/03-sql-login.sql` |
| **time sync** | tickets carry timestamps; > 5 min skew between pod and DC = rejected | chrony on the NKP node image |

### Secrets path: CyberArk → Vault → External Secrets → Secret → pod

CyberArk is the source of truth for the `svc-sqlprobe` password and rotates it in AD.
Vault holds a synced copy at `kv/nkp/sqlprobe` (`username`, `password`). In the cluster,
External Secrets Operator authenticates to Vault with its ServiceAccount token (Vault
auth method `kubernetes`), reads that KV entry every `refreshInterval` (1 h), and
writes Secret `sqlprobe-ad-credentials`. The Deployment **mounts** that Secret as
files at `/krb5/creds`, not as environment variables, on purpose: see rotation below.

### Inside the pod: one container, two processes (no sidecar)

There is no sidecar. The image's `entrypoint.sh` does the Kerberos work and then
*becomes* the app. What `ps` shows inside a running pod:

```
PID 1   dotnet /app/SqlProbe.dll        <- the app (bash replaced itself with it via exec)
PID 13  /bin/bash /app/entrypoint.sh    <- the renew loop, forked before the exec
          \_ sleep 14400                 <- waits 4 h, then runs kinit again
```

Timeline at container start (bash is PID 1 at that point):

1. Reads `/krb5/creds/KRB5_USER` and `/krb5/creds/KRB5_PASSWORD`, two files: the
   mounted Secret `sqlprobe-ad-credentials`.
2. Writes `/tmp/krb5.conf` with realm `ITCS.LOCAL` and KDC `10.12.54.14`
   (skipped if a `KRB5_CONFIG` file is mounted).
3. Runs `kinit` with the password. The KDC returns a TGT, written to
   `/tmp/krb5cc.new`, then **renamed** to `/tmp/krb5cc`.
4. Forks a background copy of itself that loops forever: sleep `KRB5_RENEW_SECONDS`
   (4 h), re-read the password file, kinit into a new file, rename. That is PID 13.
   On failure it retries every 30 s.
5. Unsets `KRB5_PASSWORD` in its own environment.
6. `exec dotnet SqlProbe.dll`. Bash is gone, PID 1 is now the app. The loop child
   keeps running because it is a separate process. If the first kinit failed, the app
   still starts and `/readyz` reports the SQL error: the pod is *not Ready* instead
   of crash-looping.

How the app uses it: the app has `KRB5CCNAME=FILE:/tmp/krb5cc` in its environment.
When it opens a SQL connection with `Integrated Security=true`, the Kerberos library
reads that file, asks the KDC for a service ticket for `MSSQLSvc/sql01.itcs.local:1433`,
and SqlClient sends the ticket to SQL Server. **The app never reads the password file
and never calls kinit. It only reads the cache file.**

`SQLPROBE_AUTH=sql` skips all of this and uses a local SQL login from a Secret.

### Renewal and rotation: what happens while the app runs

| Event | What happens | App impact |
|---|---|---|
| **Ticket renewal** (every 4 h) | the loop runs a fresh `kinit` (not `kinit -R`) with the current password: new 10 h ticket in `/tmp/krb5cc.new`, atomic rename over `/tmp/krb5cc` | none. SqlClient reads the cache only when it opens a **new** connection; open pooled connections stay logged in (Kerberos is used at login only) |
| **Password rotation** by CyberArk | AD password changes → Vault synced → ESO rewrites the Secret (≤ 1 h) → kubelet updates the mounted files in place (≤ ~1 min) → the loop reads the **new** password at its next kinit | none, no restart. The ticket obtained with the old password stays valid until it expires. A renewal that lands inside the sync window fails once and is retried 30 s later |
| **Pod restart** | entrypoint runs kinit at start with whatever the Secret holds at that moment | pod is Ready once the first SQL login succeeds |
| **Renew loop killed** (should not happen) | nothing renews; the current ticket works until it expires (≤ 10 h), then new connections fail, `/readyz` → 503, pod not-Ready | this is the trade-off of a single container vs a sidecar that Kubernetes would restart. The same script has a `kinit-loop` mode for a sidecar if that guarantee is required |

Why the rename: kinit writing directly into `/tmp/krb5cc` truncates it first, so a
connection opening at that instant would find an empty cache. Write-then-rename is
atomic; the app always sees either the old ticket or the new one.

Why files and not `envFrom`: environment variables are frozen at container start, so a
rotated password would only be seen after a restart. Mounted Secret files (no `subPath`)
are refreshed in place by the kubelet, so the loop always kinits with the current
password. A keytab would work too (`KRB5_KEYTAB`), but it is a second artifact to
regenerate on every rotation, which the password path avoids.

### Why not a domain user + password in the connection string?

On Linux, Microsoft.Data.SqlClient has no NTLM. `User Id=ITCS\jdoe;Password=…` is
NTLM on Windows and simply fails on Linux. Kerberos is the only way to be a domain
user from a Linux pod, and the password is still needed — but only by `kinit`, once
per renewal, never by the application code. A Kubernetes app that only needs *a* login
can use SQL authentication instead; Kerberos is for "log in as an AD identity".

## 2. The app

ASP.NET Core minimal API, one file (`src/SqlProbe/Program.cs`), Microsoft.Data.SqlClient 7.1.

| Endpoint | Purpose |
|---|---|
| `GET /healthz` | liveness, no DB |
| `GET /readyz` | readiness: opens a SQL connection, 503 with the error text if it fails |
| `GET /db/whoami` | **the verdict**: `LoginName`, `AuthScheme` (`KERBEROS` / `SQL`), server name, version, `EncryptOption`, client IP as SQL sees it |
| `GET /db/notes`, `POST /db/notes` | creates `dbo.ProbeNotes` on first use and writes rows (proves write access, and `LoginName` per row) |
| `GET /krb` | Kerberos diagnostics: `KRB5*` env, `klist` output, the krb5.conf in use |

A successful Kerberos run returns from `/db/whoami`:

```json
{ "LoginName": "ITCS\\svc-sqlprobe", "AuthScheme": "KERBEROS", "EncryptOption": "TRUE",
  "ServerName": "SQL01", "ClientNetAddress": "10.12.52.x", "Pod": "sqlprobe-7c9d…" }
```

Configuration is by environment variables (from `k8s/10-config.yaml` or `.env`):

| Variable | Meaning |
|---|---|
| `SQLPROBE_SERVER` | `host,port`. **FQDN for Kerberos** |
| `SQLPROBE_DATABASE` | default `master` |
| `SQLPROBE_AUTH` | `integrated` (AD user via Kerberos, default) or `sql` |
| `SQLPROBE_USER` / `SQLPROBE_PASSWORD` | sql mode only (Secret `sqlprobe-sqlauth`) |
| `SQLPROBE_SPN` | optional explicit `Server SPN` if it differs from `host:port` |
| `SQLPROBE_TRUST_SERVER_CERT` | default `true` (lab SQL has a self-signed cert). TLS is always on |
| `SQLPROBE_DEBUG` + `Logging__LogLevel__Default=Debug` | forward SqlClient's internal trace (connect, TLS, login, SSPI) to the log |
| `KRB5_CREDS_DIR`, `KRB5_USER`, `KRB5_PASSWORD`, `KRB5_KDC`, `KRB5CCNAME`, `KRB5_RENEW_SECONDS`, `KRB5_KEYTAB` | see entrypoint above |
| `ConnectionStrings__Default` | full connection string; overrides everything above |

At startup the app logs one connection attempt (`Startup probe: connected … in N ms`
or `Startup probe: FAILED after N ms — …`), so `kubectl logs` tells the story on its own.

## 4. Runbook

### 4.1 Build (Nexus)

```bash
cp .env.example .env && vi .env      # REGISTRY + Nexus proxies, SQL target, AD user
scripts/build-push.sh                # or: docker build -t sqlprobe:0.1.0 .   (public upstreams)
```

The Dockerfile pulls from three upstreams, each replaceable by a Nexus proxy in
`.env`: mcr.microsoft.com (`BASE_REGISTRY`: sdk + aspnet images), docker.io
(`DEBIAN_IMAGE` = `debian:trixie-slim`), NuGet (`NUGET_SOURCE`, plus
`NUGET_USERNAME`/`NUGET_PASSWORD` for an authenticated feed; the password is passed
as a BuildKit secret and never lands in a layer), and Debian apt (`APT_MIRROR` for
suite *trixie*, `APT_SECURITY_MIRROR` for *trixie-security*). The runtime is plain
Debian 13 because mcr has no GA .NET 10 image on trixie; the ASP.NET runtime is
copied from the official image. NKP nodes must trust the Nexus TLS CA to pull.

### 4.2 Test with docker before Kubernetes

```bash
docker run -d --name sqlprobe --env-file .env -p 18080:8080 sqlprobe:0.1.0
curl -s localhost:18080/db/whoami | jq
docker logs sqlprobe | grep -E "entrypoint|Startup probe"
```

With `SQLPROBE_AUTH=integrated` the entrypoint runs kinit with `KRB5_USER`/`KRB5_PASSWORD`
from `.env` (env instead of mounted files; same code path). `scripts/run-local.sh` does the same and then
hits every endpoint; `--debug` adds SqlClient tracing in the foreground.

### 4.3 SQL Server side (sysadmin, once)

Run `ad/03-sql-login.sql`: database `SqlProbe`, `CREATE LOGIN [ITCS\svc-sqlprobe] FROM WINDOWS`,
database user with `db_datareader`, `db_datawriter`, `db_ddladmin`, and
`GRANT VIEW SERVER STATE` (needed by `/db/whoami`). SQL Server must listen on TCP
1433 and the Windows firewall must allow it from the NKP node subnet.

### 4.4 AD side (Domain Admin, once)

Windows:

```powershell
.\ad\01-prepare-ad.ps1 -SqlFqdn sql01.itcs.local        # account (AES-only) + SPN check/registration
```

Linux (account only):

```bash
scripts/create-ad-account-ldap.sh       # AD_ADMIN_PASSWORD, SVC_NAME, SVC_PASSWORD from .env
```

Then store the account and its password in CyberArk and let it own rotation.

**SPN check.** The SPN is owned by SQL Server's own service account and is normally
already there from the SQL Server installation; the app account has nothing to do with
it. Just confirm it exists (in the ITCS lab on 2026-09-24 it did not, because there is
no SQL Server in that domain):

```powershell
setspn -Q MSSQLSvc/sql01.itcs.local:1433          # must return the SQL service account (or SQL01$)
# only if missing: setspn -S MSSQLSvc/sql01.itcs.local:1433 <account SQL Server runs as>
```

### 4.5 Deploy to NKP

```bash
# credentials Secret: EITHER ESO from Vault (target env) …
cp k8s/25-externalsecret.yaml.example k8s/25-externalsecret.yaml && vi k8s/25-externalsecret.yaml
# … OR a manual Secret from .env (test)
scripts/make-ad-secret.sh                           # → k8s/20-ad-credentials-secret.yaml
vi k8s/10-config.yaml                               # SQLPROBE_SERVER (FQDN), KRB5_KDC
vi k8s/30-deployment.yaml                           # image: <nexus>/nkp/sqlprobe:<tag>
kubectl apply -f k8s/
kubectl -n sqlprobe get pods -w                     # Ready = Kerberos login to SQL succeeded
kubectl -n sqlprobe logs deploy/sqlprobe | grep -E "entrypoint|Startup probe"
scripts/verify.sh                                   # AuthScheme must be "KERBEROS"
```

The readiness probe is a real SQL login, so a pod is only Ready when ticket, SPN and
SQL login all work. Liveness is process-only, so a SQL outage marks pods not-Ready
without restarting them. Password rotation needs no action on the cluster (see
"Rotation" above); changing the *account name* is a Secret change plus rollout restart.

**No-AD fallback:** set `SQLPROBE_AUTH: "sql"` in `10-config.yaml`, run
`scripts/make-sqlauth-secret.sh`, apply. Proves network + image before Kerberos.

## 5. Network requirements (pod egress; Cilium masquerades to node IPs by default)

| From | To | Port | Why |
|---|---|---|---|
| NKP nodes | AD DC 10.12.54.14 | 88/tcp | Kerberos AS/TGS (`udp_preference_limit=1` forces TCP) |
| NKP nodes | SQL Server | 1433/tcp | TDS |
| pods | cluster DNS → upstream | 53 | `sql01.itcs.local` must resolve in-cluster |

If `itcs.local` does not resolve from a pod, add a CoreDNS forward stub for the zone
to `10.12.54.14` (ConfigMap `coredns` in `kube-system`), declaratively.

## 6. Troubleshooting

`Content root path: /app` and `Now listening on: http://0.0.0.0:8080` are normal.
The lines that matter are `entrypoint: kinit OK|FAILED` and `Startup probe: …`.

| Symptom | Cause |
|---|---|
| `Startup probe: FAILED after 15000 ms — … network-related …` | TCP 1433 never answered: firewall, wrong host, DNS. Check: `kubectl -n sqlprobe exec deploy/sqlprobe -- curl -sv --max-time 5 telnet://sql01.itcs.local:1433` |
| `entrypoint: kinit FAILED` + `Preauthentication failed` | wrong password in the Secret (CyberArk/Vault/ESO not in sync yet, or a stale manual Secret) — the loop retries every 30 s |
| `entrypoint: kinit FAILED` + `Cannot contact any KDC` | port 88 to `KRB5_KDC` blocked |
| `KDC has no support for encryption type` | account not AES-enabled (`msDS-SupportedEncryptionTypes=24`) |
| `The target principal name is incorrect. Cannot generate SSPI context` / `Server not found in Kerberos database` | SPN `MSSQLSvc/<fqdn>:<port>` not registered, or `SQLPROBE_SERVER` is an IP / short name / not the SPN host |
| `GSSAPI … No credentials cache found` | kinit never succeeded; see `/krb` |
| `Clock skew too great` | pod/node time vs DC > 5 min |
| `Login failed for user 'ITCS\svc-sqlprobe'` | **Kerberos worked.** `ad/03-sql-login.sql` not applied (state in the SQL error log: `EXEC xp_readerrorlog 0,1,N'Login failed'`) |
| `Login failed for user 'sqlprobe'` (sql mode) | state 58 = Windows-auth-only server, 5 = no such login, 8 = wrong password, 38/40 = database missing |

Verbose: set `SQLPROBE_DEBUG: "true"` and `Logging__LogLevel__Default: "Debug"` in
`10-config.yaml` for SqlClient's internal trace, `KRB5_TRACE: "/dev/stderr"` for GSSAPI.

## 7. Verified in the lab (2026-09-24, jump host, no domain-joined SQL Server available)

- Image builds on Debian trixie with .NET 10.0.12 and SqlClient 7.1.0, with and without
  the Nexus proxy args; NuGet credential passed as a BuildKit secret leaks into no layer.
- SQL login end to end (`AuthScheme: SQL`, table created, rows written) against a
  throwaway SQL Server 2022 container, via `docker run --env-file .env`.
- `kinit` against the real ITCS KDC inside the image as UID 1654 with a read-only
  rootfs, with a password and with a keytab; renew loop and `klist -s` OK.
- Credentials mounted as files: principal read from `/krb5/creds`, password absent from
  the app process environment, a rotated password file is what the loop reads next,
  and a failed kinit leaves no temporary cache behind.
- Integrated login reaches the Kerberos service-ticket step and fails with "target
  principal name is incorrect" only because the throwaway SQL container has no SPN.
- Pod runtime shape (ConfigMap values, Secret files mounted 0400, tmpfs `/tmp`,
  read-only rootfs, non-root) simulated with `docker run`; manifests parse.
- Not verified: `AuthScheme: KERBEROS` itself. itcs.local contains only the DC and
  Nutanix Files, no SQL Server and no `MSSQLSvc` SPN. That is the remote test.
